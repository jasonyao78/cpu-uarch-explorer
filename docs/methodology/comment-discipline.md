# 注释与文档纪律（comment discipline）

> 适用范围：本仓全部新写代码（Python / C++ / CMake / Shell）。2026-09-24 起强制，存量已按此整改。
> 原则：**注释解释"为什么"，代码表达"是什么"**。维护者三年后读代码时，缺的从来不是代码复述，而是决策依据。

## 规则

1. **模块头部必有 docstring/注释块**：模块职责一句话 + 设计锚点（关联的 ADR / open-item / 评审 / 实测结论）。没有锚点的模块要回答"为什么它存在"。
2. **公开函数与类必有 docstring**：写契约——输入、输出、副作用、错误语义（抛什么/返回什么状态）。不复述实现步骤。
3. **非显然决策必须留"为什么"**：魔法数、保守取舍、 workaround 旁边注明依据与出处（评审结论、commit、实测数据），格式如 `# GB10 教训：...`、`# OI-5 实测：...`。没有出处的常量禁止出现。
4. **反模式锚点**：从缺陷/评审中学到的教训，在防线代码旁标注教训来源（例：`resolve.py` 的"静默降级禁令"、`engine.py` 的反模式对照表）。防线没有注释等于没有防线。
5. **语言**：注释用中文（与仓内文档一致），标识符与日志输出用英文。
6. **禁止**：复述代码的注释（`i += 1  # 递增 i`）、注释掉的死代码、过期注释。注释与代码在同一提交内同步修改——改代码不改注释视为缺陷。
7. **C++ 探针范本**：`probes/cache-mem/ptr_chase.cpp` 头部的"技术原理"节（为什么这样测、曾经的坑、口径与平台能力探针的联动）是本仓注释密度的基准线。
8. **测试代码同样适用**：测试模块 docstring 写明守的是什么契约/防的是哪个历史缺陷。

## 例外

- 一次性脚本（scripts/ 下的临时工具）可从简，但头部仍需一句用途。
- 自动生成的文件不注释，但生成器要注明生成方式。
