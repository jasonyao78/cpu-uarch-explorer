# SM8650 X4 P0″ demand/prefetch 正式复测裁定

**实施日期**：2026-09-28
**目标**：`redmi-k70pro-01` / SM8650 / CPU7 Cortex-X4
**范围**：512→640 KiB 机制判别 + 私有 L2 容量信号容许性；LLCC 维持封锁
**计划**：`docs/superpowers/plans/2026-09-28-sm8650-x4-p0prime-demand-prefetch.md`
**触发**：2026-09-28 外部评审驳回前一轮裁定（两份评审更正块在册）

## 1. 裁定（按预注册规则，无事后改写）

1. **规则 3（512→640 KiB 机制）：PASS（近端解释，高置信）——预取
   活动/覆盖代理量的崩塌与跳变稳定伴生。** `l1d_cache_hwprf` 在
   ≤512 KiB 为 656–929/1k（短训练）与 751–929/1k（长训练），到
   576–640 KiB 崩塌至 21–137/1k 与 62–305/1k；`l1d_cache_miss`
   互补上升（短：185→349→675→982/1k；长：72→250→~500–600→
   919/1k）。**4 个 seed × 2 个训练量 × 10 进程全部同格局**；评审
   smoke（33%→96.1% miss、67%→3.9% hwprf）在正式协议下复现成立。
   措辞边界（2026-09-28 复审）：这是当前**最直接的近端解释
   （proximal explanation）**——`l1d_cache_hwprf` 的计数语义（请
   求/填充/命中）未鉴定，预取器停止工作的**上游原因**（置换/索引
   共振、容量或其他因素）亦未鉴定，**不得表述为已决定性排除置
   换/索引共振**。
2. **规则 4（私有 L2 容量信号容许性）：FAIL —— 容量读数不容许，
   X4 私有 L2 维持 OPEN/INCONCLUSIVE。**
   - leg (a) 跨 seed 一致性：**失败**。1024 KiB 长训练同尺寸跨 seed/run
     散布 2.16 → 22.3/1k（10×）；768 KiB 长训练单个 seed 离群 14×
     （9.83 vs 其余 0.69–0.84/1k）。
   - leg (b) 跨训练量一致性：**失败**。短/长训练系统性分歧（3072 KiB：
     130–143 vs 61–63/1k；2048 KiB：80–92 vs 39–46/1k；1024 KiB：
     11.6–16.7 vs 2.2–22.3/1k）。demand L2 miss 的幅度依赖预取训练量，
     不是尺寸的纯函数。
   - leg (c) 页策略分组：**未执行**（见 §5 动态 ceiling drift 事
     件；short-THP 8/8 前置门禁失败、long-THP 未执行）。
   - 推论：任何从该曲线读取物理容量（512 KiB / 1 MiB / 2 MiB）的尝试
     都不容许；`sm8650.dtsi`（CPU7 L2 = 2 MiB，Qualcomm review）保持为
     平台描述证据，行为证据不足以支持或否决它。
3. **规则 2（事件 sanity）：PASS。** 6 个事件全部跨 regime 相干计数，
   无 always-zero：`mem_access_rd` 基线 1003–1062/1k（短训练窗口开销
   ~5–6%，长训练 ~0.3%，见 §6 残差 6）；`l1d_cache_miss` 185→982/1k；
   `l1d_cache_hwprf` 929→21/1k；`l2d_cache_miss` 0.4→143/1k；
   `l2d_cache_hwprf` 9→1043/1k。
4. **规则 1（测量完整性）：base 子矩阵 PASS；P0″ 完整矩阵
   PARTIAL。** 五个 run 共 148 条记录：115 ok + 33 failed（结构化
   失败，schema v2 空 metrics + `failure`）；去除 3 个重复的
   1024 KiB 锚点后为 **112 个唯一成功 base 条件（56 short + 56
   long）**——base 子矩阵完整。short-THP 8/8 前置门禁失败、
   long-THP 未执行，**规则 4c 未执行**。全部采用样本
   `running == enabled`、逐样本 `seed`/backing 入档；两次 ceiling
   drift 事件均被门禁 fail-closed 拦下，governor 每次均恢复
   `walt`。

## 4. 逐条预注册规则裁定

1. **完整性：base 子矩阵 PASS；完整矩阵 PARTIAL。** 148 条记录：
   115 ok + 33 failed（去 3 个重复锚点后 112 个唯一成功 base 条
   件）；失败记录空 metrics + 结构化 `failure`（schema v2）；全部
   采用样本 `running==enabled`、backing=base、seed 逐样本一致；
   每 case 前后门禁 `policy_result.valid=true`。
2. **事件 sanity：PASS。** §1.3。
3. **机制判别：PASS（近端解释）。** §1.1；判别用的是预注册的
   `l1d_cache_hwprf` 标准，非事后叙述；上游原因未鉴定（措辞边界
   见 §1.1）。
4. **容量容许性：FAIL。** §1.2；按规则 4，维持 OPEN/INCONCLUSIVE，
   不做几何排除、不引用起始沿、不提拔任何名义值。
5. **解释边界：遵守。** 未对 refill 类通用事件做幅度换算（本矩阵根本
   未使用 `0x17`）；DTS 与设备 dump 仅作平台证据登录（§6）。
6. **报告纪律：遵守。** 逐样本数据入库（records.jsonl + analyzer 附
   件）；双峰个案在案；THP 段推迟有明确触发条件（§7）。

## 5. 动态 cpufreq ceiling drift 事件时间线（测量纪律档案）

> 命名说明（2026-09-28 复审）：入库证据只证明 `scaling_max_freq`
> 被动态下调；**事发时未采集 cooling-device 状态**（取证缺口），
> CPU 峰值 52.6 °C、Android thermal status=0——既不能证明没有厂
> 商限制，也不能证明限制来自 thermal/NSP。定名"动态 cpufreq
> ceiling drift，疑似 OEM thermal/power policy 干预，**根因
> OPEN**"。

- **drift #1（02:44–02:46Z）**：long-base 在 b1024K-seed20260928
  后置门禁失败：`policy2/5 max 2707200→2630400、policy7
  2745600→2688000`，CPU 峰值 52.6 °C。runner fail-closed 中止后
  续 25 case 并恢复 governor；数分钟后限额自行恢复。前置 31
  case 的门禁在各自测量时刻有效，数据保留。
- **应对**：长训练矩阵拆为 r2a（16 case）+ r2b（12 case）两段，段间
  冷却检查；两段均 100% ok 完成。
- **drift #2（02:52Z）**：short-thp 前置门禁失败
  （`policy2/5=2572800、policy7=2630400`，CPU 46.9 °C），8 case
  未产生任何测量；runner 恢复 governor 成功。
- **持续 drift**：随后 ≥40 分钟空载观察，`scaling_max_freq` 未
  回画像值；thermal status=0、冷却设备（Android 层）空闲、电池
  28.9–32.2 °C。本文原记"仅 NSP 域传感器 54–61 °C 偏热"——
  **复审更正**：那是 `dumpsys thermalservice` 的 **cached 字段**
  （复审实测：cached 显示 CPU7 89.9 °C / NSP ~55 °C 时，Current
  HAL 温度只有 CPU7 31.9 °C / NSP ~31 °C），cached 不可当实时
  值；NSP 因果关系**不定案**。按纪律不抑制热保护，THP 段推迟
  （§7 触发条件）。
- 设备最终状态：governor 全部 `walt`，无未完成环境事务；部署探针保留
  待后续段使用。

## 6. 平台/几何证据（仅登录，不作基线）

1. `sm8650.dtsi`（上游补丁 v3，Qualcomm 维护者 review）：CPU7 L2 =
   `2097152` B；A720/A520 L2 = 512 KiB；L3 = 12 MiB；L1 I/D = 64 KiB。
2. 运行内核（HyperOS，6.1.118-android14-11）：sysfs `cache/index0-3`
   目录存在但 size/ways/sets 属性为空；`/proc/device-tree` 无
   `cache-size` 属性。本机寄存器级几何暂不可得。
3. Arm TRM（公开）：X4 L2 可选 512 KiB / 1 MiB / 2 MiB、8 路、PIPT、
   动态偏置替换——任何行为裁定都必须给 PFN 着色留位置（本轮数据已
   反复证明）。
4. 预取器身份未鉴定；`l1d_cache_hwprf`/`l2d_cache_hwprf` 的精确计数
   语义（请求数/填充数/命中数）只按官方事件名使用，未进一步分解。

## 7. 剩余不确定性与下一门禁

1. **THP 段补跑（规则 4c 收尾）**：触发条件 = `scaling_max_freq`
   四 policy 回画像值且稳定 ≥5 分钟 + 块前后 base 锚点一致（复审
   preflight 已确认限额恢复、`ready_for_transaction=true`；稳定
   性待观察）。drift 若复发，当前块 fail-closed；此前数据是否保
   留由块前后锚点决定，不能只看单 case 门禁。补跑只影响"页策略
   是否解释 >2MiB 方差"的叙述完整性，**不改变规则 4 的 FAIL 与
   容量 OPEN 状态**（leg a/b 已失败）。
2. 容量问题的可能出路（全部后置、需用户批准再立项）：PFN 着色控制
   （连续大页/指定物理布局）、干扰编排（OI-11 P2 行）、多链带宽模式
   （OI-11 P1 行）。当前数据不支持其中任何一条捷径。
3. `mem_access_rd` 基线 ~1003–1062/1k 的窗口固定开销（短训练 ~5–6%、
   长训练 ~0.3%）解释为窗口边界每进程固定量，未单独证伪。
4. ceiling drift 的根因（厂商限额策略）不透明；`dumpsys
   thermalservice` 的 cached 温度字段不可作实时证据（§5）。平台
   画像的 `cpufreq_max_khz` 门禁与 drift 的相处方式（更长冷却间
   隔、分段矩阵、块前后锚点）已在本轮演练并有效。
5. X4 私有 L2：**OPEN/INCONCLUSIVE 维持**。LLCC/外层 cache：**维持封
   锁**，解锁条件不变（私有 L2 可识别 + 用户批准）。
