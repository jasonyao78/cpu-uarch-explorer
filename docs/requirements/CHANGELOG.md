- **热管理层系统分析（2026-09-27 v6）**：设备上热管理三件套实测——mi_thermald（动态管理 scaling_max，stop 后重启见其把 policy7 cap 从 2745600 提到 3110400，实锤活动控制者）、vendor.miperf + perf2-hal（perf lock/boost 角色）。**双层频率闸门实证**：①governor=performance 只锁到 scaling_max，锁不住 mi_thermald 对 scaling_max 本身的调节；②停 mi_thermald + scaling_max=3302400 + performance，负载下 cur_freq 仍封顶 2745600——3302400 是 boost 频率，无 perf lock 不解锁。**已有 sweep 数据免疫性确认**：锁频期间 Thermal Status=0、CPU Tj 78-84°C/电池 32°C、freq 快照全程恒定 → 未被热节流过；但 mi_thermald 可随时下调 scaling_max，长跑 benchmark（GB6/SPEC）必须带 thermal 时间序列否则数据不可比。后续：环境事务扩展 thermal 抑制 controller（停/启 mi_thermald + scaling_max 固定 + 前后 thermal 快照，仅分钟级微基准使用，Tj<95°C 安全窗口）。分析参考：[Thermal Engine 原理剖析](https://www.cnblogs.com/linhaostudy/p/18649571)（高通温控架构：sensor/algo(ss,monitor,pid)/cooling device，与本机 mi_thermald 同构）。
- **thermal 抑制 controller 落地 + 12MB L3/SLC 定案（2026-09-27 v7）**：①`svc.thermal` 环境事务受控项（stop/start mi_thermald，仅 adb 执行器，非法值/非 Android 平台结构化拒绝；安全窗口=分钟级微基准 Tj<95°C，长跑 benchmark 禁止抑制）；`redmi-k70pro-01` 声明 `host_requirements: {"svc.thermal": "stopped"}`——任何 --env 运行自动附带 thermal 抑制 + 逆序恢复，`aux_snapshots` 每 case 前后采 Thermal Status/电池温度。runner 77 测试全绿。②L3/SLC 定案 **12MB、8 核共享**（用户外部情报 + X4 全速平台恰好终止于 12M 加密采样互证；A520 有效 8-10M 系 slice 分配权重差异而非容量差异；20M+ 长尾为 bonus 池稀释非硬边界）。
- **共享性干扰实验 + 方法学缺口登记（2026-09-27 v8）**：重流 32M 并发实证——cpu2-4 重流下 X4 8M/12M 不变（5.52/5.97ns）、16M 退化（8.66ns）；X4 重流下 A520 ≤6M 不变。结论：各核型有**静态保护份额**（X4≈12M / A520≈8M），溢出区为竞争敏感共享 bonus 池；与官方"12MB CPU L3 + 6MB CPU/GPU SLC"的逻辑分区口径相容，但**物理分层不可由单核延迟法证实**（SCID 同阵列、延迟相近即合并为一级）。方法学缺口：①单核延迟法测不出共享结构→干扰实验应进标准 probe 集；②GPU 共享性未测（需 GPU 负载源）；③≥16M 尾部混 4K 页 TLB 效应；④容量应报告"保护份额+溢出上限+竞争敏感性"三维而非单点。
