> 基线状态：已落盘（tag `req-v0.3`，2026-09-23）。
> 相对上一版的修正：Android 目标设备确认为一台；补全 M4 Pro 与 x86-64 服务器平台画像；D9300 实机入册（在手，后置启用）；§4 系统架构、§5 目录结构、§9 校准误差目标补全；新增许可证与数据模型决策。

## 1. 项目定位

构建一个面向未来开源的、跨 ISA 和跨 OS 的 CPU 微架构探索平台：

```text
真实设备微架构探测
→ 统一实验协议和数据模型
→ gem5 O3建模与实机校准
→ 综合Benchmark验证
→ ARM、x86和RISC-V对比
→ RISC-V自定义指令与NPU探索
```

当前主线：将已有 ARM 实机探测 Demo 工程化，以联发科 D9300 的 gem5 O3 模型完成实机校准闭环，同时支持 Apple Silicon、x86-64 Linux 和 Android ARM64。

当前迭代焦点（本轮之后的下一个里程碑）：在 Apple M4 Pro（macos-arm64）单平台跑通"probe 源码 → 统一 JSON 数据 → 自动报告"的最小骨架，再横向扩展到其余 backend。

**作为 Host**：主仓开发、本地构建、ARM64 原生编译、Python 实验编排、ADB/SSH 控制、数据分析与报告、小规模 gem5 开发和调试。

**作为 Target**：P-Core/E-Core 微架构探测、指令 latency/throughput、Branch、Cache、TLB 和 Memory 探测、P/E Core 差异分析、多线程同步和 Cache coherence 实验、Unified Memory 系统特征分析。

**已知约束**：即使具有 `sudo`，macOS 仍不等价于 Linux root 环境：无 `perf_event_open`；CPU 精确绑核能力有限（QoS 控制 P/E 归属，`THREAD_AFFINITY_POLICY` 仅为 hint）；Raw PMU 公开接口受限（`powermetrics` 为毫秒级 cluster 级采样，Instruments/xctrace 可访问部分 KPC 计数器）；DVFS 和 idle 控制受系统限制；线程可能在同一 QoS/performance level 内迁移。因此必须实现 macOS capability discovery，不能假定管理员权限等价于完整硬件控制能力。

**已实测能力（2026-09-24，证据等级 MEASURED）**：`hw.nperflevels=2`；perflevel0=Performance 10 核，perflevel1=Efficiency 4 核；`hw.cpufamily=399882554`；品牌串 "Apple M4 Pro"。`sudo powermetrics` 可用采样器：cpu_power / gpu_power / ane_power / thermal / sfi / tasks / interrupts 等；输出支持 text 与 plist（NUL 分隔，机器可读）；`--show-cpu-qos`、`--show-hwp-capability`、`--show-plimits`、`--show-pstates` 可暴露 QoS 分布、频率能力与限频信息；支持毫秒级采样率与 SIGINFO 即时采样（可脚本化）。

**计时器与 QoS 分流（2026-09-24 实测，证据等级 MEASURED，工具 `probes/platform/`）**：`mach_absolute_time` timebase 125/3（1 tick = 41.67ns，相邻调用 74.8% 落在同一 tick），单次调用开销 4.06ns——单次计时区间下限约 42ns，微基准按 ≥10^5 loads/区间设计即可让量化噪声被平均掉。QoS→P/E 分流可靠生效：延迟链吞吐在 USER_INTERACTIVE/DEFAULT（≈1.6~1.8 ns/iter）与 BACKGROUND（≈5.2~6.1 ns/iter）之间双峰，三次会话实测比值 2.6~3.9× 随频率状态漂移，**双峰结构稳定可复现——比值不作为常量引用**，测量须带重复次数与统计量（ADR-0006）；**BACKGROUND 即 E-core 测量的调度手段**（macOS 无精确绑核的替代路径）。

**仍待验证（转为环境决策，非阻塞）**：xctrace/Instruments 未安装（`xcrun` 确认本机无 Xcode），per-thread KPC 计数器可用性待安装后验证；计时法微基准不依赖 PMC，分支 probe 与 throughput 校准时再议。

## 4. 系统架构

```text
┌────────────┐   ┌────────────┐   ┌────────────┐   ┌────────────┐
│  Probe 层   │   │ Runner 层  │   │ 数据/报告层 │   │  校准层     │
│ C++17 微基准│──▶│ Python 编排 │──▶│ JSONL+报告  │──▶│ gem5 对比  │
│ 每 backend  │   │ 部署/采集/  │   │ SQLite(推迟)│   │ 差异单驱动 │
│ 同一份源码  │   │ capability │   │ 证据标签    │   │ 知识缺口   │
└────────────┘   └────────────┘   └────────────┘   └────────────┘
```

- **统一实验协议**：同协议、同语义、同参数、同数据 schema、同报告模板，所有 backend 一视同仁。可移植探针（如 ptr_chase）保持同一份源码；指令级等天然依赖 ISA 的实验，一致性锚定在 ExperimentSpec（测什么/参数/指标定义，ADR-0006），ISA 专用实现按 `kernels/<isa>/` 组织。backend 的差异只收敛在 Runner 的 target 适配层（部署方式、绑核/QoS 手段、计时器、capability discovery）。
- **Capability discovery**：每个 Target 首次接入时先运行能力探测（可用 PMU/计数器接口、绑核手段、锁频/thermal 控制、计时器精度），结果随 run 记录，禁止假定某平台具备 Linux 式完整控制能力（macOS 尤其如此）。
- **数据流**：probe 输出 → JSONL 原始记录（含元数据信封）→ 报告生成；跨 run 汇总分析待需要时引入 SQLite（schema 已按可迁移设计）。
- **校准闭环**：实机 MEASURED 数据 vs gem5 SIMULATED 数据，差异超阈值时产出"校准差异单"；解释不了的差异进入知识缺口清单，反哺 probe 或模型（详见 §9）。

**runs 管理策略**（2026-09-24，ADR-0008 后补）：run 目录中 `records.jsonl` / `artifacts.jsonl` / `run-manifest.json` 必须入库——它们才是数据层本体（ADR-0003：JSONL 是唯一 source of truth），体量小且是永久证据；`raw/`（probe 原始 stdout/stderr）**不入库**——可再生中间产物，占 run 目录约 83% 体量，完整性由 artifact-manifest 的 SHA256 锚定，需要时按记录参数重跑再生。raw 本地保留；晋升 baseline 的 run 如需长期保留原始样本，压缩归档至 `data/private/` 或 HDD 冷存储。

## 9. 校准误差目标（正式目标）

| 层级 | 指标 | 目标 | 优先级 |
|---|---|---|---|
| T1 必达 | 指令 latency | ±1 cycle | 1 |
| T1 必达 | L1/L2/LLC 延迟 | ±5~10% | 2 |
| T2 应达 | throughput、TLB 容量/延迟、分支 mispredict 率、内存带宽 | ±10% | 3 |
| T3 挑战 | Geekbench 子项 / SPEC CPU 分 | ±10~15% | 4 |

**校准顺序**：latency 表 → throughput → cache/TLB → branch → 内存 → 综合分（上层指标依赖下层，下层未对齐前不调上层）。

**铁律**：microbenchmark 用于校准（允许调参）；Geekbench/SPEC 只用于验证（不许回头调参）。验证集上的误差才代表模型泛化能力。
