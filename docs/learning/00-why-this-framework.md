# 00 · 为什么需要这个框架（问题本质）

> 费曼段：一句话——**没有纪律的测量产生的是数字，不是知识。**

## 概念

想象你要量一张桌子的长度。你有一把尺，但：每次用不同的尺、不记室温、不记量的哪里、写报告时把量失败的次数扔掉、还把 64MiB 看成 64MB。量出来的数看起来都很精确（小数点后四位），但三个月后你自己都无法复现——这就是没有工程化的微架构测量。

这个框架做的事，用一句大白话说：**把"量桌子"变成"任何人在任何一台机器上按同一份方案量，量出来的数能直接比"**。为此它定了四样东西：

1. **同一份测量工具**（探针源码，一处维护）；
2. **同一份实验方案**（ExperimentSpec，JSON 写的，机器可读）；
3. **同一张记录单**（run-record schema，每个数字带：什么时候、哪台机器、哪版代码、什么参数、重复几次）；
4. **失败也算数**（测失败了就记"失败+原因"，不许编一个数补上）。

## 为什么这么轴

本仓的真实教训（ADR-0003 背景）：前人留下的 SM8550 cache 数据只有一个数字，没日期、没机型、没代码版本——现在**连机主都不记得是哪台设备测的**，证据等级只能标 UNKNOWN，等于没有。评审又实证了参考仓（GB10 项目）的六处实现缺陷：配置写 `64MiB` 被静默当成 1024KB、声明重复 7 次实际只跑 1 次……每一条都是"看起来在干活，实际产出假数据"。

## 费曼自测

1. 为什么"小数点后四位"不等于"精确"？（答：精确=可复现+可溯源，不是位数多）
2. 框架里哪个机制保证"失败不编数"？（run-record v2：failed 记录空 metrics + 结构化 failure，schema 强制）
3. 如果让你加一个指标但不许改 schema 结构，可以吗？（可以，`additionalProperties=true`，登记 README 即可）
