# 04 · 四层架构：为什么 probe、runner、数据、报告要分开

> 费曼段：一句话——**工厂流水线分工：探针只造零件，runner 只组装，数据层只管存档，报告层只管讲故事。**

## 概念

### 分层与职责

```text
Probe 层（C++）      → 只负责"测一次，测准"：单一职责、无统计、无文件 IO
Runner 层（Python）  → 只负责"怎么跑"：计划、重复、控制、收集
数据层（JSONL+schema）→ 只负责"记下来"：每个数字可溯源
报告层（analysis/）   → 只负责"讲出来"：读记录出报告，不回写
```

### 为什么要分

反例是参考仓（GB10 项目）的教训：runner 里用 scenario 字符串前缀匹配探针（`if "cache-latency" in scenario_id`），**新增一个实验就要改主流程**——测量逻辑、调度逻辑、数据逻辑缠在一起，改一处坏三处。

分层的收益各自独立成立：

- **探针纯粹**：C++ 探针不碰统计，它的输出对不对只看 ABI 契约（03 页）；
- **runner 可换平台**：平台差异收敛在配置（controls）和执行器（local/ssh），主流程零特判；
- **数据层独立演化**：JSONL + schema 定死，未来加 SQLite 汇总层不用动采集端；
- **报告层是消费者**：读 records.jsonl 出报告，报告写错了重生成就是，原始数据不动。

### "测什么"与"怎么跑"分离（ADR-0006 的魂）

跨平台一致性不锚定在文件名或代码行，而锚定在 **ExperimentSpec**："测什么、参数、指标定义"是一份 JSON；ISA 相关的实现差异收进 `kernels/<isa>/`；平台差异收进 `configs/platforms/`。同一份 Spec 在 M4 Pro、Xeon、GB10 上跑出来的记录可以直接对比——**这才是"跨平台"三个字的实际内容**。

## 费曼自测

1. 为什么统计不放探针里？（统计口径要全框架统一；探针内统计会掩盖探针纯度问题）
2. 报告层如果发现 bug 要重算，数据会坏吗？（不会，报告是只读消费者，重跑即可）
3. 新增一个平台要动哪几层？（只动 configs/platforms/ + 可能的执行器；探针层不动——portable 探针同源码）
