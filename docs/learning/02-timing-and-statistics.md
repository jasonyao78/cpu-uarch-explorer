# 02 · 计时与统计：41.67ns 的尺子怎么量 1ns 的东西

> 费曼段：一句话——**尺子太粗就别量单根头发，量一万根头发的总长再除。**

## 概念

### 计时器分辨率是硬约束

M4 Pro 实测（OI-5，`probes/platform/macos-arm64/timer_resolution`）：`mach_absolute_time` 的 timebase 是 125/3，即 **1 tick = 41.67ns**；相邻两次调用 74.8% 落在同一 tick（读数相同）。这意味着：**单次计时区间的下限约 42ns**——比这个短的区间，测出来的可能是 0。

而我们要测的 L1 延迟只有约 1ns。用 42ns 的尺子量 1ns 的东西，单次测量毫无意义。

### 解法：装得够多，噪声就被平均掉

ptr_chase 不逐 load 计时，而是**一个区间装几百万次 load**（默认 2²⁸ 次，约百毫秒级），总时间 ÷ 总次数。量化误差是±1 tick（±41.67ns），分摊到 2.7 亿次 load 上，相对误差降到 10⁻⁴ 以下。设计规则：**计时区间 ≥10⁵ 次 load**（按 ~1ns/load 反推）。

### 为什么还要重复 5 次取中位数

平均掉的是计时器量化噪声，平均不掉的是**环境干扰**：系统中断、其他进程、频率漂移。这些让单次区间测量整体偏高（干扰只会拖慢，不会加速——分布是右偏的）。所以框架层把每个 case 重复 5 次，取 **median**（对右偏离群值天然鲁棒），同时记 min/p25/p75/max 供审计。

### 探针纯粹性原则

**探针只做单次测量，重复和统计是 runner 层的职责**（measurement-discipline §3）。理由：探针内做统计会掩盖"探针本身是否纯净"的问题；统计口径集中在 runner，所有探针一视同仁。

## 测量

计时器与 QoS 探针本身就是本仓的第一批测量成果（OI-5，2026-09-24 关闭）：分辨率 41.67ns、调用开销 4.06ns——这两个数反过来决定了所有后续微基准的参数下限（min_loads=4,194,304 就是这么来的）。

## 费曼自测

1. 为什么干扰是右偏的，median 因此比 mean 合适？（中断只会增加耗时；median 丢弃长尾）
2. min_loads=4M 这个数怎么来的？（10⁵ load 下限 × 安全余量，对着 41.67ns 分辨率反推）
3. 如果某平台计时器分辨率是 1ns，min_loads 可以放松吗？（可以但没必要——量级余量本来就是保守设计）
