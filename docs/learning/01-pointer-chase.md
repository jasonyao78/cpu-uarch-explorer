# 01 · 指针追逐：怎么测出"一次内存访问的真实延迟"

> 费曼段：一句话——**让每一步的地址都藏在上一步读出来的数据里，CPU 就没法作弊。**

## 概念

**要测的东西**：load-to-use latency——从发出一次 load 到数据可用，要经过多少纳秒。这个延迟随数据所在层级变化：L1 ≈ 1ns，L2 ≈ 几 ns，DRAM ≈ 上百 ns。把工作集从小到大扫一遍，延迟曲线的台阶就画出了 cache 层次结构。

**为什么不能顺序读**：CPU 有个"猜你喜欢"的硬件叫预取器（prefetcher）。你顺序读，它提前把后面的数据都取好了——你测的是预取器的预测能力，不是内存延迟。

**指针追逐的做法**：把缓冲区切成 64 字节一格（一个 cacheline），每格里写下一格的地址，随机打乱后首尾相连成环。沿链走：`p = *p`。每下一步的地址**来自上一步读出的值**——在数据回来之前，CPU 连下一步去哪都不知道，无法预取、无法并行。

关键性质：**MLP=1**（Memory-Level Parallelism，访存级并行度为 1）。任何时刻最多只有 1 个 load 在飞。

## 三个坑（都踩过或防过）

1. **多链陷阱**：早期版本用 4 条独立环链"摊薄循环开销"——但 4 条独立链 = 4 个并行 load，MLP=4，延迟被摊薄近 4 倍，L1 测出 0.42ns 的荒谬值。**任何引入并行性的"优化"都会改变被测量本身**。修复：严格单链。
2. **循环开销**：循环控制（计数、比较、跳转）每迭代约 1~2 周期，在 L1 尺度（~5 周期）上不可忽略。修复：同一条链展开 8 次——8 个 load 仍严格串行，控制开销摊薄 8 倍，不引入并行性。
3. **编译器优化**：如果编译器发现链上读出的值没被使用，会把整条追逐删掉。修复三重保障：mmap 真实内存（编译器看不见内容）+ 真实数据依赖 + 结果写进 volatile 变量强制物化。

## 测量

M4 Pro 实测（2026-09-24，`data/public/runs/`）：P-core L1 ≈ 0.77ns → 中间层 ≈ 7ns（256KiB 起）→ DRAM ≈ 123ns；E-core 1.4ns → 184ns。台阶位置与 P/E 双核型清晰可辨。
