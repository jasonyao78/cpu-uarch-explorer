# 09 · gem5 overlay 与最小集：一次用哈希破案的故事

> 费曼段：一句话——**1008 个文件的"增量"里，真正不一样的只有 134 个——用内容指纹逐个比对，谎言无处藏身。**

## 概念

### overlay 是什么

gem5 是上游开源模拟器。我们的 D9300 模型改动不放 fork、不改 submodule，而是存在一个独立的**增量树**里（与上游相同的目录结构），构建前用 `apply_patchset.sh` 把增量文件拷进 submodule 工作树。submodule 永远纯净，增量永远可 review。

### 问题：增量树里到底什么是"增量"？

收到的增量树有 1008 个文件，文档说"867 改 + 50 新"。但这是相对某个未知旧基线的口径。钉的上游是 v25.1——增量相对 v25.1 的真实面目是什么？

### 破案工具：blob 哈希普查

git 里每个文件内容对应一个 SHA1 指纹（blob）。对增量树每个文件算指纹，跟上游各 release tag 同路径文件比对：

| 候选基线 | 吻合数 |
|---|---:|
| v25.1.0.1（当时钉的） | **0** |
| **v25.0.0.1** | **873** |
| v24.1.0.3 | 659 |

**873/1008 与 v25.0.0.1 逐字节相同**——它们不是"修改"，是旧基线文件的**原样携带**。携带的后果很阴险：sync 时它们把 v25.1 的新版文件**静默回退**成旧版（抽样实证：isa.cc 的 diff 是在删 v25.1 的新代码）。

### 修剪与三次构建失败

删 873 携带文件 → 剩 135 个真增量。之后 Xeon 重建三连败，每次失败都抓到一个真问题：

1. `m5.internal` 引用失效——保留的 SConscript 是 v25.0 布局，引用了 v25.1 已删除的目录（当时还钉着 v25.1）；
2. `IQUnit` 模块缺失——v25.1 把 O3 的 IQ 重构拆出了新 SimObject，v25.0 增量结构性不兼容 → **裁定改钉原生基线 v25.0.0.1**（零移植还原原项目已验证状态）；
3. `CheckerCPU` 未注册——增量树**自带**的不自洽（注销了 CheckerCPU 却保留 DummyChecker 注册），该文件恢复上游后 135 → 134。

最终：v25.0.0.1 + 134 文件，干净重建 + SE 冒烟通过（2026-09-25）。`apply_patchset.sh` 从此带**基线断言 + 脏树检测**，这类问题在同步阶段就拦截。

## 费曼自测

1. 为什么"文件在增量树里"不等于"它是增量"？（可能是旧基线的原样携带，sync 时反而回退上游）
2. 基线断言防的是什么？（钉错基线时同步产生版本混合树——编译期才爆，甚至不爆而行为漂移）
3. 为什么改钉 v25.0.0.1 比移植 v25.1 先赢？（校准闭环要的是可用的模型；移植 746 行有意改动 + O3 重构适配是独立里程碑）
